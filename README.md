## 10. Selected Software Process Model

### Prototype Model

The **Prototype Model** has been selected for the development of the Car Pooling System. In this model, an initial version of the proposed system is developed with the most important features and user interfaces. The prototype is then evaluated by users or stakeholders, and their feedback is used to identify missing requirements, usability problems, and necessary modifications.

The development process is repeated through multiple iterations until the prototype sufficiently satisfies the identified user requirements. The refined prototype can then serve as the foundation for the development of the final system.

The Prototype Model is particularly suitable for the Car Pooling System because users need to interact with several workflows, including offering a ride, searching for rides, viewing ride details, and booking seats. Developing an early working prototype allows the team to demonstrate these workflows and obtain feedback before investing significant effort in the complete system.

    ## 11. Justification of the Prototype Model

The Prototype Model is suitable for the Car Pooling System for several reasons.

### 11.1 User Interface Requires Feedback

The system contains several user-facing workflows, including registration, ride creation, ride searching, ride booking, and dashboard management. It can be difficult to determine the most convenient interface for these operations before users interact with the system.

Developing an early prototype allows users to evaluate the interface and suggest improvements.

### 11.2 Requirements May Evolve

The exact requirements of a car pooling platform may not be completely clear at the beginning of development. For example, users may later identify the need for additional ride information, different booking procedures, or improved search options.

The Prototype Model allows these requirements to be discovered and refined through repeated feedback.

### 11.3 Early Demonstration

A working prototype can be demonstrated at an early stage. This allows the client or instructor to understand the proposed system without waiting for the complete application.

### 11.4 Better Requirement Validation

Instead of relying only on written requirements, stakeholders can interact with the prototype. This makes it easier to identify misunderstandings between the development team's interpretation and the actual user expectations.

### 11.5 Reduced Requirement Risk

Developing a prototype before complete implementation reduces the risk of developing features that do not satisfy user needs.

### 11.6 Suitable for a Semester-Long Project

The prototype developed in Lab 2 can be refined in later stages of the semester. Feedback obtained from the initial prototype can guide the design and implementation of additional features in future labs.

### 11.7 Suitable for the Car Pooling Domain

Car pooling involves several interactions between drivers and passengers. Demonstrating these interactions through a prototype makes it easier to validate the complete user workflow before implementing more complex functionality.
